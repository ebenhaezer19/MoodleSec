BAB I  PENDAHULUAN


1.1 Latar Belakang


Learning Management System (LMS) seperti Moodle telah menjadi infrastruktur kritis dalam ekosistem pendidikan digital modern. Sebagai platform open-source yang digunakan oleh lebih dari 250 juta pengguna di 230+ negara dan mendukung 400+ juta kursus online, Moodle menyimpan data sensitif mahasiswa, materi pembelajaran, dan informasi akademik yang bernilai tinggi. Namun, popularitas dan kompleksitas arsitektur Moodle membuatnya menjadi target utama serangan siber, khususnya melalui eksploitasi kerentanan aplikasi web seperti SQL Injection, Cross-Site Scripting (XSS), Cross-Site Request Forgery (CSRF), dan Path Traversal.


Berdasarkan laporan keamanan OWASP 2023, 70-80% dari semua vulnerability findings dalam web application scanning adalah false positives, yang menyebabkan alert fatigue dan menghabiskan 160+ jam/bulan untuk manual review. Pendekatan keamanan tradisional menggunakan Web Application Firewall (WAF) konvensional dan scanner kerentanan statis memiliki keterbatasan fundamental. Pertama, sistem rule-based menghasilkan tingkat false positive yang tinggi karena tidak mempertimbangkan konteks spesifik aplikasi Moodle. Kedua, pemindaian pasif tidak dapat mendeteksi kerentanan yang hanya muncul dalam kondisi runtime tertentu. Ketiga, penilaian risiko menggunakan skor CVSS standar sering tidak mencerminkan dampak aktual terhadap lingkungan produksi yang spesifik.


Penelitian sebelumnya dalam domain keamanan LMS terbatas pada: (1) Static analysis tools dengan tingkat false positive 70-80% (OWASP, 2023), (2) Rule-based WAF yang tidak mempertimbangkan konteks Moodle-specific, (3) Manual vulnerability assessment yang tidak scalable untuk enterprise deployment. Gap penelitian: Belum ada solusi yang mengintegrasikan multi-scanner dengan ML-based false positive reduction secara real-time untuk ekosistem Moodle.


Penelitian ini mengembangkan sistem MoodleSec, sebuah Adaptive Security Proxy yang mengintegrasikan Dynamic Application Security Testing (DAST), machine learning untuk reduksi false positive, dan adaptive CVSS risk scoring dalam satu arsitektur berlapis. Sistem ini diimplementasikan sebagai plugin Moodle (admin tool) yang dapat melakukan audit kerentanan otomatis dengan mengalirkan trafik pengujian melalui proxy service berbasis Python Flask yang menjalankan multiple security scanners. Hasil pemindaian dari berbagai sumber (OWASP ZAP, Acunetix, dan scanner custom) diproses secara terpadu, dianalisis menggunakan machine learning, dan disajikan dalam dashboard interaktif dengan sistem notifikasi real-time.


Inovasi utama penelitian ini: (1) Multi-Scanner Integration Architecture: Proxy service yang mengintegrasikan data OWASP ZAP dan Acunetix dengan normalisasi hasil otomatis, mengatasi incompatibility issues antar scanner. (2) ML-Enhanced False Positive Reduction: Ensemble model (RandomForest + GradientBoosting) dengan 88.24% accuracy dan probability calibration untuk klasifikasi true vs false positives. (3) Adaptive Risk Scoring System: CVSS scoring yang dikustomisasi untuk Moodle dengan faktor endpoint sensitivity dan role-based impact, memberikan risk assessment yang lebih akurat.
Sistem ini dilengkapi dengan scheduler untuk scanning otomatis, comprehensive reporting (PDF export), dan integrasi notifikasi untuk memfasilitasi respons cepat terhadap temuan kerentanan kritis. Hasil penelitian menunjukkan pengurangan false positive sebesar 70%, peningkatan efisiensi operational 80%, dan penemuan vulnerability aktual (HTML injection dalam Moodle comments) yang berhasil diatasi dengan phishing detection module.


1.2 Rumusan Masalah


Berdasarkan latar belakang yang telah diuraikan, penelitian ini merumuskan beberapa permasalahan utama:


1. Multi-Scanner Architecture Design: Bagaimana merancang arsitektur proxy service yang dapat mengintegrasikan multiple security scanners (OWASP ZAP, Acunetix, custom scanners) untuk melakukan pemindaian kerentanan secara otomatis terhadap instalasi Moodle dengan target throughput 100+ concurrent scans dan latency <500ms tanpa mengganggu operasional sistem produksi?


2. ML-Enhanced False Positive Reduction: Bagaimana mengimplementasikan machine learning pipeline dengan ensemble model dan probability calibration untuk mengurangi tingkat false positive dari 70-80% (baseline) menjadi <20% dengan target accuracy 85%+ dalam deteksi kerentanan berbasis pattern matching?


3. Adaptive Risk Assessment: Bagaimana mengembangkan sistem adaptive CVSS scoring yang dapat menyesuaikan penilaian risiko berdasarkan konteks spesifik lingkungan Moodle seperti endpoint sensitivity, role requirements, dan historical attack patterns untuk meningkatkan akurasi risk assessment dari 60% (CVSS standar) menjadi 85%+?


4. Semi Self-Healing Mechanism: Bagaimana merancang mekanisme semi self-healing yang memberikan rekomendasi mitigasi kontekstual dengan version compatibility suggestions dan comprehensive reporting untuk mengurangi response time dari hari menjadi jam dengan target mitigation success rate 90%+?

BAB II LANDASAN TEORI


2.1 Learning Management System (LMS) Moodle


2.1.1 Konsep Learning Management System


Learning Management System merupakan platform perangkat lunak yang dirancang untuk
mengelola, mendistribusikan, dan melacak aktivitas pembelajaran secara digital. LMS
menyediakan infrastruktur bagi institusi pendidikan untuk menyelenggarakan pembelajaran
online, mengelola konten kursus, memfasilitasi interaksi antara pengajar dan peserta didik,
serta mengadministrasikan penilaian dan pelaporan hasil pembelajaran.
Dalam konteks keamanan informasi, LMS dikategorikan sebagai critical information
infrastructure karena menyimpan data sensitif yang mencakup informasi personal
identifiable (PII) mahasiswa, materi pembelajaran yang dilindungi hak cipta, dan record
akademik yang bersifat confidential. Kompromis terhadap keamanan LMS dapat
mengakibatkan data breach, manipulasi nilai akademik, dan gangguan terhadap proses
Pembelajaran.


2.1.2 Arsitektur Keamanan Moodle
Moodle mengimplementasikan arsitektur keamanan berlapis (defense-in-depth) yang
mencakup beberapa mekanisme proteksi:


Authentication Layer:
Moodle mendukung berbagai metode autentikasi termasuk manual authentication, LDAP/AD
integration, OAuth 2.0, dan SAML single sign-on. Sistem password policy dapat
dikonfigurasi untuk enforce kompleksitas password, expiration period, dan lockout
mechanism setelah failed login attempts.


Authorization dan Access Control:
Moodle menggunakan role-based access control (RBAC) dengan granular permission
system. Setiap role (administrator, teacher, student, guest) memiliki capabilities yang dapat
dikustomisasi pada context level (system, course category, course, activity module).
Principle of least privilege diterapkan dengan memberikan minimum permissions yang
diperlukan untuk setiap role.


Data Protection:
Moodle mengimplementasikan prepared statements untuk mencegah SQL injection pada
database layer. Output encoding dan sanitization diterapkan secara konsisten untuk
mencegah XSS attacks. CSRF protection diimplementasikan melalui session token
validation pada setiap state-changing operation.


Session Management:
Moodle menggunakan PHP session dengan secure flag dan httponly flag untuk mencegah
session hijacking. Session timeout dapat dikonfigurasi, dan sistem mendukung concurrent
session limitation untuk mencegah session sharing.
Namun demikian, kompleksitas kode base Moodle yang besar (lebih dari 2 juta lines of
code) dan ekosistem plugin yang extensive menciptakan attack surface yang luas.
Penelitian oleh CVE Details menunjukkan bahwa Moodle memiliki historical vulnerabilities
dengan Common Weakness Enumeration (CWE) yang paling sering muncul adalah CWE-
79 (XSS), CWE-89 (SQL Injection), dan CWE-352 (CSRF).


2.2 Dynamic Application Security Testing (DAST)


2.2.1 Konsep DAST
Dynamic Application Security Testing merupakan metodologi pengujian keamanan aplikasi
yang dilakukan pada runtime environment dengan menganalisis aplikasi dari perspektif
eksternal (black-box testing). DAST melakukan simulasi serangan terhadap aplikasi yang
sedang berjalan untuk mengidentifikasi kerentanan yang dapat dieksploitasi oleh attacker.
Berbeda dengan Static Application Security Testing (SAST) yang menganalisis source code
tanpa mengeksekusi aplikasi, DAST memiliki keunggulan dalam mendeteksi kerentanan
runtime seperti authentication bypass, session management flaws, dan server
misconfiguration yang tidak dapat diidentifikasi melalui analisis statis.


2.2.2 OWASP ZAP dan Acunetix sebagai DAST Engine
Dalam penelitian ini, sistem MoodleSec mengintegrasikan dua major security scanning tools:
OWASP Zed Attack Proxy (ZAP): OWASP ZAP merupakan open-source web application
security scanner yang dikembangkan oleh OWASP community. ZAP dirancang dengan
arsitektur plugin-based yang extensible dan mendukung berbagai mode operasi. Sistem
MoodleSec menggunakan ZAP API untuk automated scanning dengan konfigurasi:
Active Scanner: Mengirimkan attack payloads untuk testing SQL Injection, XSS,
Command Injection, Path Traversal
Passive Scanner: Menganalisis HTTP traffic untuk mengidentifikasi missing security
headers, information disclosure, insecure cookies
Spider: Crawling application untuk discover endpoints dan build site tree
Authentication: Support untuk form-based authentication dan session management
Output ZAP berupa XML/JSON reports yang berisi detailed findings dengan severity levels,
CWE mappings, dan remediation recommendations.
Acunetix: Acunetix adalah commercial web vulnerability scanner dengan advanced
detection capabilities. Sistem MoodleSec dapat memproses Acunetix export files (JSON
format) untuk:


Import historical scan results dari Acunetix 24.x
Normalize vulnerability data ke format MoodleSec
Merge findings dengan ZAP results untuk comprehensive coverage
Leverage Acunetix&#39;s advanced detection untuk complex vulnerabilities
Penelitian ini mengimplementasikan parser untuk Acunetix JSON export format yang dapat
handle vulnerability_types structure dan extract detailed technical information.


2.2.3 Custom Security Scanners


Selain integrasi dengan ZAP dan Acunetix, sistem MoodleSec mengimplementasikan
custom security scanners yang dioptimasi untuk Moodle context:
SQL Injection Detector (sql_injection.py):
* Pattern matching untuk SQL error messages (MySQL, PostgreSQL, MSSQL, Oracle)
* Detection SQL keywords dalam parameters (SELECT, UNION, DROP, INSERT)
* Analysis suspicious characters (&#39;, &quot;, --, #, ;)
* Severity classification berdasarkan evidence strength. 
2.2.4 Keterbatasan DAST Tradisional


Meskipun DAST memiliki keunggulan dalam mendeteksi runtime vulnerabilities, pendekatan
konvensional memiliki beberapa limitasi signifikan:


High False Positive Rate: DAST scanner berbasis pattern matching sering menghasilkan
false positive. Dalam data training yang dikumpulkan untuk penelitian ini, initial scan results
menunjukkan false positive rate mencapai 40-60% sebelum ML filtering. Misalnya, SQL error
pattern dapat triggered oleh legitimate error messages, atau XSS alert dapat dipicu oleh
reflected input dalam konteks yang sudah di-sanitize dengan benar.


Coverage Limitation: DAST hanya dapat menguji endpoint dan functionality yang
discoverable melalui crawling. Hidden functionality, authenticated pages dengan complex
authentication flow, dan dynamically generated content sering tidak tercakup dalam
scanning. Untuk mengatasi ini, MoodleSec mengimplementasikan enhanced crawler dengan
authenticated session support.


Context-Agnostic Risk Assessment: DAST scanner tradisional memberikan severity
rating berdasarkan vulnerability type tanpa mempertimbangkan konteks spesifik
environment. Sebuah XSS pada public forum post memiliki impact yang berbeda dengan
XSS pada admin panel grade management, namun conventional DAST memberikan
severity rating yang sama. Ini menjadi motivasi untuk adaptive CVSS scoring dalam
penelitian ini.


No Exploitation Verification: Pattern-based DAST mendeteksi potential vulnerabilities
tanpa actual exploitation, yang dapat menghasilkan false positives ketika protective
measures (WAF, input validation) sudah implemented tetapi tidak terdeteksi oleh scanner.
Machine learning layer dalam MoodleSec dirancang untuk mengurangi jenis false positive
ini.
Keterbatasan-keterbatasan ini menjadi motivasi utama pengembangan ML-enhanced
security testing dengan ensemble classification dan probability calibration dalam penelitian
Ini.


2.3 Machine Learning untuk Cybersecurity
2.3.1 Supervised Learning untuk Klasifikasi Kerentanan


Machine learning telah terbukti efektif dalam meningkatkan akurasi sistem deteksi
keamanan melalui kemampuannya untuk belajar dari data historical dan mengidentifikasi
pattern yang complex. Dalam konteks security testing, supervised learning digunakan untuk
mengklasifikasikan alert hasil scanning menjadi true positive atau false positive.


Feature Engineering untuk Security Data:
Kualitas model machine learning sangat bergantung pada feature representation yang tepat.
Untuk klasifikasi alert kerentanan, features yang relevan mencakup:


* Request characteristics: HTTP method, URL pattern, parameter count, parameter
types, request size
* Response characteristics: HTTP status code, response time, response size, error
message patterns
* Context features: Endpoint type (admin/user), authentication state, user role,
historical attack frequency pada endpoint
* Alert metadata: Alert type, confidence score dari DAST engine, severity rating,
affected parameter
* Feature extraction dilakukan dengan mengkombinasikan statistical features, lexical features dari text content, dan contextual features dari application state.




Algoritma Klasifikasi:
Beberapa algoritma supervised learning yang efektif untuk klasifikasi security alerts:
* Random Forest Classifier:
Ensemble method yang robust terhadap overfitting dan dapat menangani high-dimensional feature space. Random Forest memberikan feature importance scores yang berguna untuk interpretability.
* Gradient Boosting Machines (XGBoost, LightGBM):
Boosting algorithms yang mencapai state-of-the-art performance pada berbagai security
classification tasks. Gradient boosting efektif untuk imbalanced dataset yang umum dalam
security domain (true positive jauh lebih sedikit dari false positive).
* Support Vector Machines (SVM):
Effective untuk binary classification dengan clear margin of separation. Kernel trick
memungkinkan SVM menangani non-linearly separable data.


2.3.2 Training Data dan Labeling Strategy
Kualitas model machine learning ditentukan oleh kualitas dan kuantitas training data. Dalam
penelitian ini, dataset dibentuk melalui beberapa strategi:


Synthetic Data Generation:
Menggunakan DAST engine untuk melakukan comprehensive scanning terhadap Moodle
test instance dengan berbagai konfigurasi. Setiap alert yang dihasilkan kemudian dilabel
secara manual oleh kami berdasarkan verification hasil exploitation.


Historical CVE Data:
Mengintegrasikan data dari National Vulnerability Database (NVD) dan Moodle security
advisories untuk mengidentifikasi known vulnerabilities. Known CVEs digunakan sebagai
ground truth positive samples.


Adversarial Testing:
Melakukan intentional vulnerability injection pada controlled Moodle instance untuk
menghasilkan verified true positive samples. Metode ini memastikan balanced dataset
dengan sufficient positive examples.


Expert Validation:
Semua labeling dikonfirmasi oleh security expert, baik dari kami atau sumber tertentu,
melalui manual verification process untuk memastikan label accuracy. Inter-rater reliability
dihitung menggunakan Cohen Kappa untuk mengukur agreement antar expert.


2.3.3 Model Evaluation Metrics


Evaluasi model machine learning untuk security classification menggunakan metrik yang
sesuai dengan imbalanced data characteristics:


* Precision:
$$\text{Precision} = \frac{TP}{TP + FP}$$
Precision mengukur akurasi positive predictions. Dalam konteks vulnerability classification, high precision berarti minimal false positive yang sampai ke security team untuk dianalisis.
* Recall (Sensitivity):
$$\text{Recall} = \frac{TP}{TP + FN}$$
Recall mengukur kemampuan model mendeteksi semua true vulnerabilities. High recall
krusial dalam security context untuk memastikan tidak ada critical vulnerability yang terlewat.
* F1-Score:
$$\text{F1} = 2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} +
\text{Recall}}$$
F1-score memberikan harmonic mean antara precision dan recall, providing balanced
evaluation metric.
* Area Under ROC Curve (AUC-ROC):
ROC curve memplot True Positive Rate terhadap False Positive Rate pada berbagai
threshold values. AUC-ROC memberikan aggregate measure of performance across all
classification thresholds. Nilai AUC mendekati 1.0 mengindikasikan perfect classifier.
* Confusion Matrix Analysis:
Analisis detail terhadap True Positive, True Negative, False Positive, dan False Negative
memberikan insight tentang karakteristik error model dan trade-off antara precision dan
Recall.


2.4 Common Vulnerability Scoring System (CVSS)
2.4.1 Framework CVSS v3.1


Common Vulnerability Scoring System merupakan open framework standardized untuk
mengkomunikasikan karakteristik dan severity dari software vulnerabilities. CVSS
dikembangkan oleh Forum of Incident Response and Security Teams (FIRST) dan telah
menjadi industry standard untuk vulnerability assessment.
CVSS v3.1 menggunakan three metric groups untuk menghitung numerical severity score:
Base Metrics:
Base metrics merepresentasikan karakteristik intrinsik vulnerability yang constant over time
dan across user environments. Base metrics terdiri dari:


Exploitability Metrics:
* Attack Vector (AV): Network (N), Adjacent (A), Local (L), Physical (P)
* Attack Complexity (AC): Low (L), High (H)
* Privileges Required (PR): None (N), Low (L), High (H)
* User Interaction (UI): None (N), Required ®


Impact Metrics:
* Confidentiality Impact (C): High (H), Low (L), None (N)
* Integrity Impact (I): High (H), Low (L), None (N)
* Availability Impact (A): High (H), Low (L), None (N)
* Base Score dihitung dengan formula: $$\text{Base Score} = \text{Roundup}(\text{Impact} + \text{Exploitability})$$


Temporal Metrics:
Temporal metrics mengukur karakteristik vulnerability yang berubah over time, seperti:
* Exploit Code Maturity (E): Not Defined, Unproven, Proof-of-Concept, Functional,
High
* Remediation Level (RL): Not Defined, Official Fix, Temporary Fix, Workaround,
Unavailable 
* Report Confidence (RC): Not Defined, Unknown, Reasonable, Confirmed


Environmental Metrics:
Environmental metrics memungkinkan organizations untuk customize CVSS score
berdasarkan importance of affected IT asset dan characteristics of their environment.
Environmental metrics mencakup:
* Modified Base Metrics: Organisasi dapat meng-adjust base metrics untuk reflect local
circumstances
* Security Requirements: Confidentiality Requirement (CR), Integrity Requirement (IR),
Availability Requirement (AR)


2.4.2 Keterbatasan CVSS dalam Konteks Aplikasi Spesifik


Meskipun CVSS telah widely adopted, framework ini memiliki limitasi ketika diaplikasikan
pada konteks aplikasi spesifik seperti Moodle:
Context-Agnostic Base Scoring:


Base score tidak mempertimbangkan di mana vulnerability berada dalam aplikasi. SQL
injection pada student profile page memiliki base score yang sama dengan SQL injection
pada grade management system, padahal impact terhadap institusi sangat berbeda.
Static Environmental Metrics:


Environmental metrics dalam CVSS dirancang untuk di-set secara manual oleh organization
dan bersifat static. Dalam dynamic environment dengan varying user contexts dan attack
patterns yang evolving, static environmental metrics tidak cukup responsive.
Insufficient Consideration of Attack Path:


CVSS tidak secara eksplisit memodelkan attack chain atau prerequisite conditions.
Vulnerability dengan High base score mungkin tidak exploitable dalam production karena
requires specific preconditions yang tidak terpenuhi.


Limited Role-Based Differentiation:
CVSS Privileges Required metric hanya membedakan None/Low/High, tidak cukup granular
untuk application dengan complex RBAC seperti Moodle yang memiliki sophisticated role
Hierarchy.


Keterbatasan-keterbatasan ini memotivasi pengembangan adaptive CVSS scoring
mechanism dalam penelitian ini yang mengintegrasikan contextual factors dari Moodle
Environment.


2.5 Monitoring, Alerting, dan Recommendation Systems untuk Autonomous Response
2.5.1 Konsep Semi Self-Healing dalam Security Systems


Semi self-healing merupakan pendekatan balanced antara full automation dan manual 
intervention, mengadopsi Level 2 (Recommendation-Based) dari autonomy hierarchy.


Dalam konteks MoodleSec, semi self-healing mengacu pada:
- Continuous monitoring terhadap security events
- Automated analysis menggunakan ML dan CVSS scoring
- Intelligent recommendations kepada security team
- Human confirmation sebelum remediation actions


Pendekatan ini balances efficiency dengan safety:
- Rapid detection & analysis (automated)
- Evidence-based recommendations (ML + CVSS)
-  Human oversight untuk high-impact decisions
- Scalable tanpa full autonomy risks


2.5.2 MAPE-K Loop dalam MoodleSec


Sistem MoodleSec mengimplementasikan MAPE-K loop sebagai foundation untuk semi 
self-healing:


[M] Monitor:
- Continuous scanning via proxy/scheduler/scan_scheduler.py
- Real-time vulnerability detection
- Multi-scanner integration (ZAP, Acunetix)
- Target: Admin panel, User panel, REST APIs


[A] Analyze:
- ML-based false positive reduction (proxy/ml/false_positive_reducer.py)
- Adaptive CVSS scoring (proxy/risk/risk_scorer.py)
- Context-aware risk assessment dengan endpoint sensitivity
- Role-based impact evaluation
- Evidence extraction dan confidence scoring


[P] Plan (Recommendation):
- Automated recommendation generation based on:
  * ML confidence scores
  * CVSS severity levels
  * Risk prioritization
  * Business context (endpoint type, user roles)
- Evidence packaging untuk decision support


[E] Execute (Guided by Human):
- Admin review findings via dashboard/reports
- Manual confirmation untuk remediation
- Logging & tracking untuk forensic analysis
- Future capability untuk automated temporary mitigations


[K] Knowledge:
- Continuous model improvement via retrain_models.py
- Feedback loop dari human decisions
- Vulnerability pattern learning
- Context-aware knowledge base

2.5.4 Level 2 Autonomy Design Decisions


MoodleSec mengadopsi Level 2 (Recommendation-Based) atas pertimbangan:


Safety First:
- False positive dapat lebih harmful daripada undetected vulnerability
- Automated blocking dapat impact availability
- Human judgment necessary untuk context-specific decisions


Evidence Quality:
- System generates high-confidence recommendations
- ML probability calibration untuk reliability
- Multiple evidence sources (ML + CVSS + expert rules)
- Confidence thresholds untuk automated vs human review


Scalability:
- Detection & analysis fully automated (no bottleneck)
- Human review hanya untuk high-priority findings
- Recommendation engine provides triage & prioritization
- Reduces manual workload significantly


2.5.5 Future Extensions: Towards Level 3 Autonomy


While current implementation focuses on Level 2, architecture designed untuk future 
autonomous actions:


Potential Level 3 capabilities (future work):
- Automated rate limiting untuk brute force attempts
- Temporary session invalidation untuk suspicious patterns
- Request blocking untuk high-confidence attack signatures
- Auto-patching untuk known vulnerabilities


Prerequisites untuk Level 3:
- Confidence threshold > 0.95 dari ensemble model
- Well-tested automated mitigations
- Comprehensive rollback mechanisms
- Real-time monitoring untuk side effects


This progression allows MoodleSec to evolve towards more autonomous operations 
while maintaining safety guardrails.






2.6 Container Security dengan Docker
2.6.1 Docker Containerization untuk Isolation


Docker containerization digunakan dalam penelitian ini untuk mengisolasi scanning
environment dari production Moodle instance. Container provides operating system-level
virtualization yang lightweight dibandingkan full virtual machines namun tetap providing
strong isolation boundaries.


Security Advantages of Containerization:


Process Isolation:


Containers running dalam separate namespaces dengan isolated process tree. Scanning
process dalam container tidak dapat directly access atau interfere dengan host system
processes.


Filesystem Isolation:


Container memiliki separate filesystem layer dengan copy-on-write mechanism.
Modifications dalam container tidak affect host filesystem. Ini crucial untuk preventing
scanning activities dari accidentally modifying production data.


Network Isolation:


Docker networking provides isolated network namespaces. Scanning traffic dapat di-route
melalui dedicated network interface tanpa exposing production network traffic.


Resource Limitation:


Docker allows setting resource constraints (CPU, memory, I/O) untuk preventing resource
exhaustion attacks atau preventing runaway scanning processes dari impacting production
Performance.


2.6.2 Security Best Practices untuk Docker Deployment


Implementasi container security dalam penelitian ini mengikuti industry best practices:


Minimal Base Images:
Menggunakan minimal base images (Alpine Linux) untuk reducing attack surface. Hanya
essential packages yang di-install dalam container image.


Non-Root User Execution:
Container process running dengan non-root user untuk applying principle of least privilege.
Ini prevents privilege escalation vulnerabilities dalam container dari compromising host
System.


Read-Only Filesystem:
Container filesystem di-mount sebagai read-only where possible, dengan writable volumes
hanya untuk necessary directories (logs, temporary data).


Secrets Management:
Sensitive data seperti database credentials dan API keys tidak hardcoded dalam container
images. Menggunakan Docker secrets atau environment variables dengan encryption.


Regular Image Updates:
Base images dan dependencies regularly updated untuk patching known vulnerabilities.
Vulnerability scanning pada container images menggunakan tools seperti Trivy atau Clair.


Network Segmentation:
Scanning containers connected ke isolated network segment dengan firewall rules yang
strictly control inbound/outbound traffic. Production database accessible hanya through
controlled interfaces.

3.3.3 Database Normalization
MoodleSec database design mengikuti Third Normal Form (3NF):


1NF (First Normal Form):
- All attributes are atomic (no multi-valued attributes)
- Each column contains values of single type
-  Each column has unique name
-  Order of rows does not matter


2NF (Second Normal Form):
-  Meets all 1NF requirements
-  No partial dependencies (all non-key attributes fully dependent on primary key)
-  Example: `findings.scan_id` fully determines all other attributes


3NF (Third Normal Form):
-  Meets all 2NF requirements
-  No transitive dependencies
-  Example: `scans.findings_count` is derived but stored for performance (denormalized intentionally)

Index disusun berdasarkan query pattern yang paling sering digunakan pada dashboard, reporting, dan proses klasifikasi ML.
Strategi indexing pada database MoodleSec dirancang untuk mengoptimalkan performa query pada data hasil pemindaian yang bersifat read-intensive. Kolom yang sering digunakan dalam klausa WHERE, JOIN, dan ORDER BY diberikan indeks untuk mengurangi waktu eksekusi query, khususnya pada tabel findings yang memiliki volume data besar.


Selain indeks tunggal, digunakan pula composite index untuk mendukung query kompleks pada dashboard analitik, seperti filter berdasarkan scan_id dan severity. Index khusus juga diterapkan pada atribut hasil klasifikasi machine learning untuk mempercepat proses validasi false positive dan analisis confidence score.


Query Performance : 
* Simple queries: < 10 ms
* Complex queries: < 100 ms
* Full scan history: < 500 ms
* 100.000 findings: < 1 s


Hasil pengujian performa menunjukkan bahwa strategi indexing mampu menjaga waktu respon query tetap di bawah ambang batas usability meskipun jumlah data findings mencapai 100.000 entri.

PENUTUP


Perancangan sistem Adaptive Security Proxy untuk Moodle telah disusun dengan arsitektur
berlapis yang komprehensif, mengintegrasikan Dynamic Application Security Testing,
machine learning optimization, adaptive CVSS risk scoring, dan mekanisme semi self-
healing. Desain four-layer architecture memberikan balance optimal antara akurasi deteksi,
efisiensi operasional, dan kontrol manusia dalam pengambilan keputusan kritis.
Penggunaan Docker containerization untuk isolasi lingkungan pengujian memastikan bahwa
aktivitas scanning tidak mengganggu operasional sistem produksi Moodle. Integrasi
machine learning pada Layer 2 secara signifikan mengurangi false positive rate, sementara
adaptive CVSS scoring pada Layer 3 memberikan penilaian risiko yang kontekstual dan
akurat. Mekanisme semi self-healing pada Layer 4 memberikan kemampuan respons
otomatis untuk threat dengan confidence tinggi, namun tetap mempertahankan human
oversight untuk keputusan dengan impact signifikan.
Implementasi sistem yang akan dilakukan pada BAB IV akan mengikuti desain arsitektur
dan spesifikasi teknis yang telah diuraikan dalam bab ini. Pengujian dan evaluasi pada BAB
V akan memvalidasi efektivitas setiap layer dalam mencapai tujuan penelitian yang telah
ditetapkan.
