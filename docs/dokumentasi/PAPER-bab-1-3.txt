PENDAHULUAN
1.1 Latar Belakang
Learning Management System (LMS) seperti Moodle telah menjadi infrastruktur kritis dalam ekosistem pendidikan digital modern. Sebagai platform open-source yang digunakan oleh jutaan institusi pendidikan di seluruh dunia, Moodle menyimpan data sensitif mahasiswa, materi pembelajaran, dan informasi akademik yang bernilai tinggi. Namun, popularitas dan kompleksitas arsitektur Moodle membuatnya menjadi target utama serangan siber, khususnya melalui eksploitasi kerentanan aplikasi web seperti SQL Injection, Cross-Site Scripting (XSS), Cross-Site Request Forgery (CSRF), dan Path Traversal.
Pendekatan keamanan tradisional menggunakan Web Application Firewall (WAF) konvensional dan scanner kerentanan statis memiliki beberapa keterbatasan fundamental. Pertama, sistem rule-based menghasilkan tingkat false positive yang tinggi karena tidak mempertimbangkan konteks spesifik aplikasi Moodle. Kedua, pemindaian pasif tidak dapat mendeteksi kerentanan yang hanya muncul dalam kondisi runtime tertentu. Ketiga, penilaian risiko menggunakan skor CVSS standar sering tidak mencerminkan dampak aktual terhadap lingkungan produksi yang spesifik.
Penelitian ini mengembangkan sistem MoodleSec, sebuah Adaptive Security Proxy yang mengintegrasikan Dynamic Application Security Testing (DAST), machine learning untuk reduksi false positive, dan adaptive CVSS risk scoring dalam satu arsitektur berlapis. Sistem ini diimplementasikan sebagai plugin Moodle (admin tool) yang dapat melakukan audit kerentanan otomatis dengan mengalirkan trafik pengujian melalui proxy service berbasis Python Flask yang menjalankan multiple security scanners. Hasil pemindaian dari berbagai sumber (OWASP ZAP, Acunetix, dan scanner custom) diproses secara terpadu, dianalisis menggunakan machine learning, dan disajikan dalam dashboard interaktif dengan sistem notifikasi real-time melalui Slack namun ini sifatnya opsional untuk sementara waktu.
Inovasi utama penelitian ini terletak pada tiga aspek: (1) Integrasi multi-scanner dengan normalisasi hasil melalui proxy service yang dapat memproses output dari OWASP ZAP dan Acunetix secara otomatis; (2) Machine learning pipeline dengan ensemble model (Random Forest dan XGBoost) yang dilengkapi probability calibration untuk meningkatkan akurasi klasifikasi true positive vs false positive; (3) Mekanisme semi self-healing yang memberikan rekomendasi mitigasi kontekstual berdasarkan adaptive CVSS scoring dengan mempertimbangkan faktor-faktor seperti endpoint sensitivity, role-based impact, dan historical attack patterns. Sistem ini dilengkapi dengan scheduler untuk scanning otomatis, comprehensive reporting (PDF export), dan integrasi notifikasi untuk memfasilitasi respons cepat terhadap temuan kerentanan kritis.

2.1 Learning Management System (LMS) Moodle
2.1.1 Konsep Learning Management System
Learning Management System merupakan platform perangkat lunak yang dirancang untuk mengelola, mendistribusikan, dan melacak aktivitas pembelajaran secara digital. LMS menyediakan infrastruktur bagi institusi pendidikan untuk menyelenggarakan pembelajaran online, mengelola konten kursus, memfasilitasi interaksi antara pengajar dan peserta didik, serta mengadministrasikan penilaian dan pelaporan hasil pembelajaran.
Dalam konteks keamanan informasi, LMS dikategorikan sebagai critical information infrastructure karena menyimpan data sensitif yang mencakup informasi personal identifiable (PII) mahasiswa, materi pembelajaran yang dilindungi hak cipta, dan record akademik yang bersifat confidential. Kompromis terhadap keamanan LMS dapat mengakibatkan data breach, manipulasi nilai akademik, dan gangguan terhadap proses pembelajaran.
2.1.2 Arsitektur Keamanan Moodle
Moodle mengimplementasikan arsitektur keamanan berlapis (defense-in-depth) yang mencakup beberapa mekanisme proteksi:
Authentication Layer:
Moodle mendukung berbagai metode autentikasi termasuk manual authentication, LDAP/AD integration, OAuth 2.0, dan SAML single sign-on. Sistem password policy dapat dikonfigurasi untuk enforce kompleksitas password, expiration period, dan lockout mechanism setelah failed login attempts.
Authorization dan Access Control:
Moodle menggunakan role-based access control (RBAC) dengan granular permission system. Setiap role (administrator, teacher, student, guest) memiliki capabilities yang dapat dikustomisasi pada context level (system, course category, course, activity module). Principle of least privilege diterapkan dengan memberikan minimum permissions yang diperlukan untuk setiap role.
Data Protection:
Moodle mengimplementasikan prepared statements untuk mencegah SQL injection pada database layer. Output encoding dan sanitization diterapkan secara konsisten untuk mencegah XSS attacks. CSRF protection diimplementasikan melalui session token validation pada setiap state-changing operation.
Session Management:
Moodle menggunakan PHP session dengan secure flag dan httponly flag untuk mencegah session hijacking. Session timeout dapat dikonfigurasi, dan sistem mendukung concurrent session limitation untuk mencegah session sharing.
Namun demikian, kompleksitas kode base Moodle yang besar (lebih dari 2 juta lines of code) dan ekosistem plugin yang extensive menciptakan attack surface yang luas. Penelitian oleh CVE Details menunjukkan bahwa Moodle memiliki historical vulnerabilities dengan Common Weakness Enumeration (CWE) yang paling sering muncul adalah CWE-79 (XSS), CWE-89 (SQL Injection), dan CWE-352 (CSRF).
2.2 Dynamic Application Security Testing (DAST)
2.2.1 Konsep DAST
Dynamic Application Security Testing merupakan metodologi pengujian keamanan aplikasi yang dilakukan pada runtime environment dengan menganalisis aplikasi dari perspektif eksternal (black-box testing). DAST melakukan simulasi serangan terhadap aplikasi yang sedang berjalan untuk mengidentifikasi kerentanan yang dapat dieksploitasi oleh attacker.
Berbeda dengan Static Application Security Testing (SAST) yang menganalisis source code tanpa mengeksekusi aplikasi, DAST memiliki keunggulan dalam mendeteksi kerentanan runtime seperti authentication bypass, session management flaws, dan server misconfiguration yang tidak dapat diidentifikasi melalui analisis statis.
2.2.2 OWASP ZAP dan Acunetix sebagai DAST Engine
Dalam penelitian ini, sistem MoodleSec mengintegrasikan dua major security scanning tools:
OWASP Zed Attack Proxy (ZAP): OWASP ZAP merupakan open-source web application security scanner yang dikembangkan oleh OWASP community. ZAP dirancang dengan arsitektur plugin-based yang extensible dan mendukung berbagai mode operasi. Sistem MoodleSec menggunakan ZAP API untuk automated scanning dengan konfigurasi:
Active Scanner: Mengirimkan attack payloads untuk testing SQL Injection, XSS, Command Injection, Path Traversal
Passive Scanner: Menganalisis HTTP traffic untuk mengidentifikasi missing security headers, information disclosure, insecure cookies
Spider: Crawling application untuk discover endpoints dan build site tree
Authentication: Support untuk form-based authentication dan session management
Output ZAP berupa XML/JSON reports yang berisi detailed findings dengan severity levels, CWE mappings, dan remediation recommendations.
Acunetix: Acunetix adalah commercial web vulnerability scanner dengan advanced detection capabilities. Sistem MoodleSec dapat memproses Acunetix export files (JSON format) untuk:
Import historical scan results dari Acunetix 24.x
Normalize vulnerability data ke format MoodleSec
Merge findings dengan ZAP results untuk comprehensive coverage
Leverage Acunetix's advanced detection untuk complex vulnerabilities
Penelitian ini mengimplementasikan parser untuk Acunetix JSON export format yang dapat handle vulnerability_types structure dan extract detailed technical information.
2.2.3 Custom Security Scanners
Selain integrasi dengan ZAP dan Acunetix, sistem MoodleSec mengimplementasikan custom security scanners yang dioptimasi untuk Moodle context:
SQL Injection Detector (sql_injection.py):
Pattern matching untuk SQL error messages (MySQL, PostgreSQL, MSSQL, Oracle)
Detection SQL keywords dalam parameters (SELECT, UNION, DROP, INSERT)
Analysis suspicious characters (', ", --, #, ;)
Severity classification berdasarkan evidence strength
CWE-89 mapping dengan detailed remediation steps
XSS (Cross-Site Scripting) Detector (xss_detector.py):
Reflected XSS detection melalui parameter value reflection dalam response
Dangerous HTML tag detection (<script>, <iframe>, <object>, <embed>)
Inline event handler detection (onclick, onerror, onload)
JavaScript protocol detection (javascript:, data:text/html)
DOM-based XSS indicators (innerHTML, eval, document.write)
Input sanitization validation
CWE-79 mapping dengan context-specific recommendations
CSRF Validator (csrf_validator.py):
CSRF token presence validation dalam forms
Token validation dalam POST/PUT/DELETE/PATCH requests
SameSite cookie attribute checking
Common token name recognition (csrf_token, sesskey, _token)
Moodle-specific sesskey validation
CWE-352 mapping dengan mitigation guidelines
Path Traversal Detector (path_traversal.py):
Path traversal pattern detection (../, ..\\, URL-encoded variants)
Sensitive file access attempts (/etc/passwd, c:\\windows\\system32\\config)
Absolute path detection dalam parameters
Directory listing indicators
File extension validation
CWE-22 mapping dengan secure coding recommendations
Scanner Engine Orchestration: Semua scanners di-orchestrate oleh scanner_engine.py yang provides:
Parallel execution untuk performance optimization
Deduplication untuk menghindari duplicate findings
Severity-based sorting (Critical → High → Medium → Low → Info)
Summary statistics generation
Per-scanner enable/disable configuration
Error handling dan resilience
Output dari scanner engine berupa structured JSON dengan format:
{
  "scan_id": "unique_scan_identifier",
  "timestamp": "ISO-8601 datetime",
  "target_url": "scanned endpoint",
  "total_findings": integer,
  "summary": {
    "critical": count, "high": count, 
    "medium": count, "low": count, "info": count
  },
  "findings": [array of vulnerability objects],
  "scanner_results": {status per scanner}
}
2.2.4 Keterbatasan DAST Tradisional
Meskipun DAST memiliki keunggulan dalam mendeteksi runtime vulnerabilities, pendekatan konvensional memiliki beberapa limitasi signifikan:
High False Positive Rate: DAST scanner berbasis pattern matching sering menghasilkan false positive. Dalam data training yang dikumpulkan untuk penelitian ini, initial scan results menunjukkan false positive rate mencapai 40-60% sebelum ML filtering. Misalnya, SQL error pattern dapat triggered oleh legitimate error messages, atau XSS alert dapat dipicu oleh reflected input dalam konteks yang sudah di-sanitize dengan benar.
Coverage Limitation: DAST hanya dapat menguji endpoint dan functionality yang discoverable melalui crawling. Hidden functionality, authenticated pages dengan complex authentication flow, dan dynamically generated content sering tidak tercakup dalam scanning. Untuk mengatasi ini, MoodleSec mengimplementasikan enhanced crawler dengan authenticated session support.
Context-Agnostic Risk Assessment: DAST scanner tradisional memberikan severity rating berdasarkan vulnerability type tanpa mempertimbangkan konteks spesifik environment. Sebuah XSS pada public forum post memiliki impact yang berbeda dengan XSS pada admin panel grade management, namun conventional DAST memberikan severity rating yang sama. Ini menjadi motivasi untuk adaptive CVSS scoring dalam penelitian ini.
No Exploitation Verification: Pattern-based DAST mendeteksi potential vulnerabilities tanpa actual exploitation, yang dapat menghasilkan false positives ketika protective measures (WAF, input validation) sudah implemented tetapi tidak terdeteksi oleh scanner. Machine learning layer dalam MoodleSec dirancang untuk mengurangi jenis false positive ini.
Keterbatasan-keterbatasan ini menjadi motivasi utama pengembangan ML-enhanced security testing dengan ensemble classification dan probability calibration dalam penelitian ini.
2.3 Machine Learning untuk Cybersecurity
2.3.1 Supervised Learning untuk Klasifikasi Kerentanan
Machine learning telah terbukti efektif dalam meningkatkan akurasi sistem deteksi keamanan melalui kemampuannya untuk belajar dari data historical dan mengidentifikasi pattern yang complex. Dalam konteks security testing, supervised learning digunakan untuk mengklasifikasikan alert hasil scanning menjadi true positive atau false positive.
Feature Engineering untuk Security Data:
Kualitas model machine learning sangat bergantung pada feature representation yang tepat. Untuk klasifikasi alert kerentanan, features yang relevan mencakup:
Request characteristics: HTTP method, URL pattern, parameter count, parameter types, request size
Response characteristics: HTTP status code, response time, response size, error message patterns
Context features: Endpoint type (admin/user), authentication state, user role, historical attack frequency pada endpoint
Alert metadata: Alert type, confidence score dari DAST engine, severity rating, affected parameter
Feature extraction dilakukan dengan mengkombinasikan statistical features, lexical features dari text content, dan contextual features dari application state.
Algoritma Klasifikasi:
Beberapa algoritma supervised learning yang efektif untuk klasifikasi security alerts:
Random Forest Classifier:
Ensemble method yang robust terhadap overfitting dan dapat menangani high-dimensional feature space. Random Forest memberikan feature importance scores yang berguna untuk interpretability.
Gradient Boosting Machines (XGBoost, LightGBM):
Boosting algorithms yang mencapai state-of-the-art performance pada berbagai security classification tasks. Gradient boosting efektif untuk imbalanced dataset yang umum dalam security domain (true positive jauh lebih sedikit dari false positive).
Support Vector Machines (SVM):
Effective untuk binary classification dengan clear margin of separation. Kernel trick memungkinkan SVM menangani non-linearly separable data.
2.3.2 Training Data dan Labeling Strategy
Kualitas model machine learning ditentukan oleh kualitas dan kuantitas training data. Dalam penelitian ini, dataset dibentuk melalui beberapa strategi:
Synthetic Data Generation:
Menggunakan DAST engine untuk melakukan comprehensive scanning terhadap Moodle test instance dengan berbagai konfigurasi. Setiap alert yang dihasilkan kemudian dilabel secara manual oleh kami berdasarkan verification hasil exploitation.
Historical CVE Data:
Mengintegrasikan data dari National Vulnerability Database (NVD) dan Moodle security advisories untuk mengidentifikasi known vulnerabilities. Known CVEs digunakan sebagai ground truth positive samples.
Adversarial Testing:
Melakukan intentional vulnerability injection pada controlled Moodle instance untuk menghasilkan verified true positive samples. Metode ini memastikan balanced dataset dengan sufficient positive examples.
Expert Validation:
Semua labeling dikonfirmasi oleh security expert, baik dari kami atau sumber tertentu, melalui manual verification process untuk memastikan label accuracy. Inter-rater reliability dihitung menggunakan Cohen's Kappa untuk mengukur agreement antar expert.
2.3.3 Model Evaluation Metrics
Evaluasi model machine learning untuk security classification menggunakan metrik yang sesuai dengan imbalanced data characteristics:
Precision:
$$\text{Precision} = \frac{TP}{TP + FP}$$
Precision mengukur akurasi positive predictions. Dalam konteks vulnerability classification, high precision berarti minimal false positive yang sampai ke security team untuk dianalisis.
Recall (Sensitivity):
$$\text{Recall} = \frac{TP}{TP + FN}$$
Recall mengukur kemampuan model mendeteksi semua true vulnerabilities. High recall krusial dalam security context untuk memastikan tidak ada critical vulnerability yang terlewat.
F1-Score:
$$\text{F1} = 2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$$
F1-score memberikan harmonic mean antara precision dan recall, providing balanced evaluation metric.
Area Under ROC Curve (AUC-ROC):
ROC curve memplot True Positive Rate terhadap False Positive Rate pada berbagai threshold values. AUC-ROC memberikan aggregate measure of performance across all classification thresholds. Nilai AUC mendekati 1.0 mengindikasikan perfect classifier.
Confusion Matrix Analysis:
Analisis detail terhadap True Positive, True Negative, False Positive, dan False Negative memberikan insight tentang karakteristik error model dan trade-off antara precision dan recall.
2.4 Common Vulnerability Scoring System (CVSS)
2.4.1 Framework CVSS v3.1
Common Vulnerability Scoring System merupakan open framework standardized untuk mengkomunikasikan karakteristik dan severity dari software vulnerabilities. CVSS dikembangkan oleh Forum of Incident Response and Security Teams (FIRST) dan telah menjadi industry standard untuk vulnerability assessment.
CVSS v3.1 menggunakan three metric groups untuk menghitung numerical severity score:
Base Metrics:
Base metrics merepresentasikan karakteristik intrinsik vulnerability yang constant over time dan across user environments. Base metrics terdiri dari:
Exploitability Metrics:
Attack Vector (AV): Network (N), Adjacent (A), Local (L), Physical (P)
Attack Complexity (AC): Low (L), High (H)
Privileges Required (PR): None (N), Low (L), High (H)
User Interaction (UI): None (N), Required (R)
Impact Metrics:
Confidentiality Impact (C): High (H), Low (L), None (N)
Integrity Impact (I): High (H), Low (L), None (N)
Availability Impact (A): High (H), Low (L), None (N)
Base Score dihitung dengan formula: $$\text{Base Score} = \text{Roundup}(\text{Impact} + \text{Exploitability})$$
Temporal Metrics:
Temporal metrics mengukur karakteristik vulnerability yang berubah over time, seperti:
Exploit Code Maturity (E): Not Defined, Unproven, Proof-of-Concept, Functional, High
Remediation Level (RL): Not Defined, Official Fix, Temporary Fix, Workaround, Unavailable
Report Confidence (RC): Not Defined, Unknown, Reasonable, Confirmed
Environmental Metrics:
Environmental metrics memungkinkan organizations untuk customize CVSS score berdasarkan importance of affected IT asset dan characteristics of their environment. Environmental metrics mencakup:
Modified Base Metrics: Organisasi dapat meng-adjust base metrics untuk reflect local circumstances
Security Requirements: Confidentiality Requirement (CR), Integrity Requirement (IR), Availability Requirement (AR)
2.4.2 Keterbatasan CVSS dalam Konteks Aplikasi Spesifik
Meskipun CVSS telah widely adopted, framework ini memiliki limitasi ketika diaplikasikan pada konteks aplikasi spesifik seperti Moodle:
Context-Agnostic Base Scoring:
Base score tidak mempertimbangkan di mana vulnerability berada dalam aplikasi. SQL injection pada student profile page memiliki base score yang sama dengan SQL injection pada grade management system, padahal impact terhadap institusi sangat berbeda.
Static Environmental Metrics:
Environmental metrics dalam CVSS dirancang untuk di-set secara manual oleh organization dan bersifat static. Dalam dynamic environment dengan varying user contexts dan attack patterns yang evolving, static environmental metrics tidak cukup responsive.
Insufficient Consideration of Attack Path:
CVSS tidak secara eksplisit memodelkan attack chain atau prerequisite conditions. Vulnerability dengan High base score mungkin tidak exploitable dalam production karena requires specific preconditions yang tidak terpenuhi.
Limited Role-Based Differentiation:
CVSS Privileges Required metric hanya membedakan None/Low/High, tidak cukup granular untuk application dengan complex RBAC seperti Moodle yang memiliki sophisticated role hierarchy.
Keterbatasan-keterbatasan ini memotivasi pengembangan adaptive CVSS scoring mechanism dalam penelitian ini yang mengintegrasikan contextual factors dari Moodle environment.
2.5 Self-Healing Systems dalam Application Security
2.5.1 Konsep Self-Healing Systems
Self-healing systems merupakan paradigma sistem yang memiliki kemampuan untuk automatically detect, diagnose, dan recover dari failures atau attacks tanpa human intervention. Dalam konteks cybersecurity, self-healing mengacu pada automated defensive mechanisms yang dapat merespons detected threats secara real-time.
Autonomic Computing Framework:
Konsep self-healing berakar pada autonomic computing yang diinisiasi oleh IBM, dengan prinsip MAPE-K loop:
Monitor: Continuous monitoring of system state dan environment
Analyze: Analisis collected data untuk detect anomalies atau threats
Plan: Merencanakan corrective actions berdasarkan analysis results
Execute: Implementasi planned actions untuk mitigate threats
Knowledge: Shared knowledge base yang evolving based on experiences
2.5.2 Tingkatan Autonomi dalam Self-Healing Security
Self-healing security systems dapat dikategorikan berdasarkan level of autonomy:
Level 1 - Alerting Only:
System hanya melakukan detection dan generate alerts untuk human operators. Tidak ada automated response. Ini adalah pendekatan traditional security monitoring.
Level 2 - Recommendation-Based:
System melakukan detection, analysis, dan generate recommended actions, tetapi requires explicit human approval sebelum execution. Ini adalah semi-autonomous approach.
Level 3 - Conditional Automation:
System dapat automatically execute predefined responses untuk well-understood threats dengan low risk of false positive, sedangkan complex cases escalated ke human operators.
Level 4 - Full Autonomy:
System independently detects, analyzes, dan executes responses tanpa human intervention. Level ini requires extremely high confidence in detection accuracy dan comprehensive understanding of potential side effects.
2.5.3 Semi Self-Healing: Balancing Automation dan Control
Penelitian ini mengadopsi pendekatan semi self-healing (Level 2-3) dengan pertimbangan sebagai berikut:
Risk Mitigation Strategy:
Full autonomy dalam security response dapat menimbulkan availability issues jika terjadi false positive. Blocking legitimate users atau disabling critical functionality dapat lebih harmful daripada potential attack. Semi self-healing memberikan safety net melalui human confirmation untuk high-impact actions.
Temporary Mitigation Actions:
System dapat automatically implement temporary protective measures dengan reversibility guarantee:
Rate limiting untuk suspected brute force attempts
Temporary session invalidation untuk suspicious activity patterns
Request blocking untuk high-confidence attack signatures
Logging enhancement untuk forensic analysis
Human-in-the-Loop Confirmation:
Untuk actions dengan potential impact pada system availability atau functionality:
System generates detailed recommendation dengan risk assessment
Admin diberikan evidence package: attack logs, confidence score, potential impact analysis
Explicit approval required sebelum execution
Rollback mechanism tersedia untuk undo actions
Escalation Criteria:
Clear criteria untuk determining kapan automated response appropriate vs requires human judgment:
Confidence score threshold (e.g., >0.95 for automated response)
Impact level (low impact = automated, high impact = human approval)
Attack pattern familiarity (known patterns = automated, novel patterns = human review)
2.6 Container Security dengan Docker
2.6.1 Docker Containerization untuk Isolation
Docker containerization digunakan dalam penelitian ini untuk mengisolasi scanning environment dari production Moodle instance. Container provides operating system-level virtualization yang lightweight dibandingkan full virtual machines namun tetap providing strong isolation boundaries.
Security Advantages of Containerization:
Process Isolation:
Containers running dalam separate namespaces dengan isolated process tree. Scanning process dalam container tidak dapat directly access atau interfere dengan host system processes.
Filesystem Isolation:
Container memiliki separate filesystem layer dengan copy-on-write mechanism. Modifications dalam container tidak affect host filesystem. Ini crucial untuk preventing scanning activities dari accidentally modifying production data.
Network Isolation:
Docker networking provides isolated network namespaces. Scanning traffic dapat di-route melalui dedicated network interface tanpa exposing production network traffic.
Resource Limitation:
Docker allows setting resource constraints (CPU, memory, I/O) untuk preventing resource exhaustion attacks atau preventing runaway scanning processes dari impacting production performance.
2.6.2 Security Best Practices untuk Docker Deployment
Implementasi container security dalam penelitian ini mengikuti industry best practices:
Minimal Base Images:
Menggunakan minimal base images (Alpine Linux) untuk reducing attack surface. Hanya essential packages yang di-install dalam container image.
Non-Root User Execution:
Container process running dengan non-root user untuk applying principle of least privilege. Ini prevents privilege escalation vulnerabilities dalam container dari compromising host system.
Read-Only Filesystem:
Container filesystem di-mount sebagai read-only where possible, dengan writable volumes hanya untuk necessary directories (logs, temporary data).
Secrets Management:
Sensitive data seperti database credentials dan API keys tidak hardcoded dalam container images. Menggunakan Docker secrets atau environment variables dengan encryption.
Regular Image Updates:
Base images dan dependencies regularly updated untuk patching known vulnerabilities. Vulnerability scanning pada container images menggunakan tools seperti Trivy atau Clair.
Network Segmentation:
Scanning containers connected ke isolated network segment dengan firewall rules yang strictly control inbound/outbound traffic. Production database accessible hanya through controlled interfaces.

API Client (api_client.php):
class api_client {
    private $base_url;
    private $timeout;
    
    public function __construct($base_url = 'http://localhost:8999') {
        $this->base_url = $base_url;
        $this->timeout = 30;
    }
    
    public function trigger_scan($config) {
        $endpoint = $this->base_url . '/scan-trigger';
        return $this->make_request('POST', $endpoint, $config);
    }
    
    public function get_scan_history($limit = 10) {
        $endpoint = $this->base_url . '/scan-history';
        return $this->make_request('GET', $endpoint, ['limit' => $limit]);
    }
    
    public function get_ml_status() {
        $endpoint = $this->base_url . '/ml/status';
        return $this->make_request('GET', $endpoint);
    }
    
    public function get_executive_summary($scan_id) {
        $endpoint = $this->base_url . '/executive-summary/' . $scan_id;
        return $this->make_request('GET', $endpoint);
    }
    
    private function make_request($method, $url, $data = null) {
        $ch = curl_init();
        curl_setopt($ch, CURLOPT_URL, $url);
        curl_setopt($ch, CURLOPT_RETURNTRANSFER, true);
        curl_setopt($ch, CURLOPT_TIMEOUT, $this->timeout);
        
        if ($method === 'POST' && $data) {
            curl_setopt($ch, CURLOPT_POST, true);
            curl_setopt($ch, CURLOPT_POSTFIELDS, json_encode($data));
            curl_setopt($ch, CURLOPT_HTTPHEADER, [
                'Content-Type: application/json'
            ]);
        }
        
        $response = curl_exec($ch);
        $http_code = curl_getinfo($ch, CURLINFO_HTTP_CODE);
        curl_close($ch);
        
        if ($http_code !== 200) {
            throw new moodle_exception('api_error', 'tool_moodlesec');
        }
        
        return json_decode($response, true);
    }
}

Scheduled Task (scheduled_scan_task.php):
namespace tool_moodlesec\task;

class scheduled_scan_task extends \core\task\scheduled_task {
    
    public function get_name() {
        return get_string('scheduledscantask', 'tool_moodlesec');
    }
    
    public function execute() {
        $api = new \tool_moodlesec\api_client();
        
        // Get scheduler configuration from settings
        $config = get_config('tool_moodlesec');
        
        if (!$config->enable_scheduled_scans) {
            mtrace('Scheduled scans disabled');
            return;
        }
        
        $scan_config = [
            'scan_type' => 'full',
            'target_url' => $CFG->wwwroot,
            'scan_intensity' => $config->scan_intensity,
            'enable_ml' => $config->enable_ml_classification
        ];
        
        try {
            $result = $api->trigger_scan($scan_config);
            mtrace('Scan initiated: ' . $result['scan_id']);
            
            // Send notification if critical findings detected
            if ($result['summary']['critical'] > 0) {
                $this->send_critical_alert($result);
            }
            
        } catch (Exception $e) {
            mtrace('Scan failed: ' . $e->getMessage());
        }
    }
    
    private function send_critical_alert($scan_result) {
        $recipients = explode(',', get_config('tool_moodlesec', 'notification_emails'));
        
        foreach ($recipients as $email) {
            email_to_user(
                (object)['email' => trim($email)],
                get_admin(),
                get_string('critical_findings_subject', 'tool_moodlesec'),
                get_string('critical_findings_body', 'tool_moodlesec', $scan_result)
            );
        }
    }
}

**Prinsip Desain Utama:**

2. **Separation of Concerns:** Setiap layer memiliki responsibility yang terdefinisi dengan jelas: deteksi (Layer 1), optimasi (Layer 2), penilaian (Layer 3), dan mitigasi (Layer 4).

3. **Progressive Enhancement:** Informasi mengalir dari layer bawah ke atas dengan progressive enrichment. Raw alerts dari DAST engine diperkaya dengan ML confidence scores, kemudian dengan adaptive risk scores, dan akhirnya dengan actionable recommendations.

4. **Fail-Safe Design:** Kegagalan pada higher layers tidak memblokir output dari lower layers. Jika ML model unavailable, sistem tetap berfungsi dengan traditional DAST results.

def ensemble_prediction(alert_features):
    # Get probability predictions from both models
    rf_prob = rf_model.predict_proba(alert_features)[:, 1]
    xgb_prob = xgb_model.predict_proba(alert_features)[:, 1]
    
    # Weighted ensemble (weights determined by validation performance)
    ensemble_prob = 0.6 * rf_prob + 0.4 * xgb_prob
    
    # Confidence score calculation
    confidence = calculate_confidence(rf_prob, xgb_prob, ensemble_prob)
    
    # Final classification dengan dynamic threshold
    threshold = adaptive_threshold(alert_features)
    classification = 'TRUE_POSITIVE' if ensemble_prob > threshold else 'FALSE_POSITIVE'

        'probability': ensemble_prob,
        'confidence': confidence,
        'rf_probability': rf_prob,

    }
Confidence Score Calculation:
Confidence score mengindikasikan seberapa yakin model terhadap prediksinya:
def calculate_confidence(rf_prob, xgb_prob, ensemble_prob):
    # Model agreement: jika kedua model setuju, confidence tinggi
    agreement = 1 - abs(rf_prob - xgb_prob)
    
    # Prediction certainty: distance dari decision boundary (0.5)
    certainty = 2 * abs(ensemble_prob - 0.5)
    
    # Combined confidence score
    confidence = (0.6 * agreement + 0.4 * certainty)
    
    return confidence

3.4.1 Baseline CVSS Calculation
Layer ini dimulai dengan standard CVSS v3.1 base score calculation, kemudian meng-adjust score berdasarkan Moodle-specific context:
CVSS Base Metrics Mapping:
def calculate_base_cvss(vulnerability_type, context):
    # Attack Vector mapping
    if context['endpoint_type'] == 'api':
        AV = 'NETWORK'  # Score: 0.85
    elif context['requires_authentication']:
        AV = 'ADJACENT'  # Score: 0.62
    else:
        AV = 'NETWORK'  # Score: 0.85
    
    # Attack Complexity
    if vulnerability_type in ['SQL_INJECTION', 'COMMAND_INJECTION']:
        AC = 'LOW'  # Score: 0.77
    elif vulnerability_type in ['XXE', 'DESERIALIZATION']:
        AC = 'HIGH'  # Score: 0.44
    else:
        AC = 'LOW'  # Score: 0.77
    
    # Privileges Required
    if not context['requires_authentication']:
        PR = 'NONE'  # Score: 0.85
    elif context['required_role_level'] <= 1:
        PR = 'LOW'  # Score: 0.62
    else:
        PR = 'HIGH'  # Score: 0.27
    
    # User Interaction
    if vulnerability_type in ['XSS', 'CSRF']:
        UI = 'REQUIRED'  # Score: 0.62
    else:
        UI = 'NONE'  # Score: 0.85
    
    # Impact metrics (simplified)
    C = I = A = 'HIGH'  # Score each: 0.56
    
    # Calculate exploitability and impact sub-scores
    exploitability = 8.22 * AV * AC * PR * UI
    impact = 1 - ((1 - C) * (1 - I) * (1 - A))
    
    # Base score calculation
    if impact <= 0:
        base_score = 0
    else:
        base_score = min(10, (impact + exploitability))
    
    return round_up(base_score)
3.4.2 Adaptive Scoring Algorithm
Adaptive CVSS scoring meng-adjust base score dengan contextual multipliers:
Contextual Adjustment Factors:
def calculate_adaptive_cvss(base_score, alert, ml_confidence):
    adaptive_score = base_score
    adjustment_factors = []
    
    # Factor 1: ML Confidence Adjustment
    # High confidence dalam true positive → increase score
    # Low confidence → decrease score (potential false positive)
    confidence_multiplier = 0.7 + (0.6 * ml_confidence)
    adaptive_score *= confidence_multiplier
    adjustment_factors.append({
        'factor': 'ML_Confidence',
        'multiplier': confidence_multiplier,
        'reasoning': f'ML model confidence: {ml_confidence:.2f}'
    })
    
    # Factor 2: Endpoint Sensitivity
    endpoint_sensitivity = get_endpoint_sensitivity(alert['context']['endpoint_type'])
    sensitivity_multipliers = {
        'critical': 1.3,  # Admin panel, grade management
        'high': 1.15,     # User data, authentication
        'medium': 1.0,    # Course content, forums
        'low': 0.85       # Public pages, static content
    }
    sensitivity_mult = sensitivity_multipliers[endpoint_sensitivity]
    adaptive_score *= sensitivity_mult
    adjustment_factors.append({
        'factor': 'Endpoint_Sensitivity',
        'multiplier': sensitivity_mult,
        'reasoning': f'Endpoint classified as {endpoint_sensitivity} sensitivity'
    })
    
    # Factor 3: Role-based Impact Amplification
    required_role = alert['context']['required_role_level']
    role_multipliers = {
        0: 0.9,   # Guest access (limited impact)
        1: 1.0,   # Student (moderate impact)
        2: 1.2,   # Teacher (elevated impact)
        3: 1.4    # Admin (critical impact)
    }
    role_mult = role_multipliers.get(required_role, 1.0)
    adaptive_score *= role_mult
    adjustment_factors.append({
        'factor': 'Required_Role',
        'multiplier': role_mult,
        'reasoning': f'Vulnerability requires role level {required_role}'
    })
    
    # Factor 4: Historical Attack Pattern
    historical_attacks = alert['context']['historical_attack_count']
    if historical_attacks > 10:
        history_mult = 1.25  # Frequently targeted endpoint
    elif historical_attacks > 5:
        history_mult = 1.1
    else:
        history_mult = 1.0
    adaptive_score *= history_mult
    adjustment_factors.append({
        'factor': 'Attack_History',
        'multiplier': history_mult,
        'reasoning': f'{historical_attacks} previous attacks on this endpoint'
    })
    
    # Factor 5: Exploitability in Production
    # Consider additional factors yang mempengaruhi real-world exploitability
    exploitability_factors = assess_production_exploitability(alert)
    exploit_mult = exploitability_factors['multiplier']
    adaptive_score *= exploit_mult
    adjustment_factors.append({
        'factor': 'Production_Exploitability',
        'multiplier': exploit_mult,
        'reasoning': exploitability_factors['reasoning']
    })
    
    # Cap score at 10.0 (CVSS maximum)
    adaptive_score = min(10.0, adaptive_score)
    
    # Determine severity category berdasarkan adaptive score
    severity = categorize_severity(adaptive_score)
    
    return {
        'base_score': base_score,
        'adaptive_score': round(adaptive_score, 1),
        'severity': severity,
        'adjustment_factors': adjustment_factors,
        'total_multiplier': adaptive_score / base_score if base_score > 0 else 1.0
    }

def assess_production_exploitability(alert):
    """Assess additional exploitability factors specific to production environment"""
    multiplier = 1.0
    reasons = []
    
    # Check if WAF/security plugins active
    if has_active_waf():
        multiplier *= 0.8
        reasons.append("Active WAF may block exploitation")
    
    # Check if endpoint has additional validation
    if has_input_validation(alert['url']):
        multiplier *= 0.85
        reasons.append("Input validation present")
    
    # Check if vulnerability requires specific configuration
    if requires_specific_config(alert):
        multiplier *= 0.9
        reasons.append("Requires specific configuration to exploit")
    
    # Check network accessibility
    if alert['context']['endpoint_type'] == 'admin' and has_ip_restriction():
        multiplier *= 0.7
        reasons.append("Admin panel has IP restrictions")
    
    reasoning = "; ".join(reasons) if reasons else "No mitigating factors found"
    
    return {
        'multiplier': multiplier,
        'reasoning': reasoning
    }

def categorize_severity(score):

        return 'HIGH'

        return 'MEDIUM'
    elif score >= 0.1:
        return 'LOW'

        return 'INFORMATIONAL'
3.4.3 Risk Prioritization Matrix
Hasil adaptive CVSS scoring dikombinasikan dengan likelihood assessment untuk menghasilkan risk priority:
def calculate_risk_priority(adaptive_cvss, ml_confidence, context):
    """
    Risk Priority = Impact (CVSS) × Likelihood (ML + Context)
    """
    
    # Impact score (normalized dari CVSS)
    impact = adaptive_cvss / 10.0  # Range: 0-1
    
    # Likelihood calculation
    likelihood_factors = {
        'ml_confidence': ml_confidence * 0.4,          # 40% weight
        'historical_attacks': min(context['historical_attack_count'] / 50, 1.0) * 0.2,  # 20%
        'endpoint_exposure': get_exposure_score(context) * 0.2,  # 20%
        'exploit_availability': check_public_exploits(context) * 0.2  # 20%
    }
    likelihood = sum(likelihood_factors.values())  # Range: 0-1
    
    # Risk score calculation
    risk_score = impact * likelihood * 100  # Range: 0-100
    
    # Priority categorization
    if risk_score >= 70:
        priority = 'P1_CRITICAL'
        sla = '24 hours'
    elif risk_score >= 50:
        priority = 'P2_HIGH'
        sla = '72 hours'
    elif risk_score >= 30:
        priority = 'P3_MEDIUM'
        sla = '1 week'
    else:
        priority = 'P4_LOW'
        sla = '1 month'
    
    return {
        'risk_score': round(risk_score, 1),
        'priority': priority,
        'recommended_sla': sla,
        'impact': round(impact, 2),
        'likelihood': round(likelihood, 2),
        'likelihood_breakdown': likelihood_factors
    }

def determine_mitigation_action(alert, risk_priority, ml_confidence):
    """
    Determine appropriate mitigation action based on:
    - Vulnerability severity
    - ML confidence level
    - Risk priority
    - Impact to availability
    """
    
    severity = alert['adaptive_cvss']['severity']
    priority = risk_priority['priority']
    
    # Decision matrix
    if ml_confidence >= 0.95 and priority == 'P1_CRITICAL':
        # High confidence, critical priority → Aggressive mitigation
        if alert['vulnerability_type'] in ['SQL_INJECTION', 'COMMAND_INJECTION']:
            return {
                'primary_action': MITIGATION_ACTIONS['TEMPORARY_BLOCK'],
                'secondary_action': MITIGATION_ACTIONS['SESSION_INVALIDATION'],
                'requires_approval': False,  # Auto-execute
                'reasoning': 'High confidence critical vulnerability - immediate blocking required'
            }
        elif alert['vulnerability_type'] in ['XSS', 'CSRF']:
            return {
                'primary_action': MITIGATION_ACTIONS['PARAMETER_VALIDATION'],
                'secondary_action': MITIGATION_ACTIONS['RATE_LIMIT'],
                'requires_approval': False,
                'reasoning': 'High confidence XSS/CSRF - apply input validation and rate limiting'
            }
    
    elif ml_confidence >= 0.85 and priority in ['P1_CRITICAL', 'P2_HIGH']:
        # Medium-high confidence → Moderate mitigation
        return {
            'primary_action': MITIGATION_ACTIONS['RATE_LIMIT'],
            'secondary_action': None,
            'requires_approval': False,
            'reasoning': 'Medium-high confidence - apply rate limiting as precaution'
        }
    
    elif ml_confidence >= 0.70:
        # Moderate confidence → Conservative mitigation dengan approval
        return {
            'primary_action': MITIGATION_ACTIONS['RATE_LIMIT'],
            'secondary_action': None,
            'requires_approval': True,
            'reasoning': 'Moderate confidence - recommend rate limiting with admin approval'
        }
    
    else:
        # Low confidence → Alerting only, no automated action
        return {
            'primary_action': None,
            'secondary_action': None,
            'requires_approval': True,
            'reasoning': 'Low confidence - alert admin without automated mitigation'
        }

Moodle Version Recommendation:
def generate_version_recommendation(vulnerabilities):
    """Recommend Moodle version based on detected vulnerabilities"""
    
    current_version = detect_moodle_version()
    vulnerable_components = identify_vulnerable_components(vulnerabilities)
    
    # Check against CVE database
    patched_versions = {}
    for vuln in vulnerabilities:
        if vuln['ml_classification']['classification'] == 'TRUE_POSITIVE':
            # Query CVE database untuk patch version
            patch_info = query_cve_patch_info(vuln['vulnerability_type'], vuln['references'])
            if patch_info:
                patched_versions[vuln['alert_id']] = patch_info
    
    # Recommend minimum safe version
    if patched_versions:
        recommended_version = determine_minimum_safe_version(patched_versions)
        
        return {
            'current_version': current_version,
            'recommended_version': recommended_version,
            'vulnerabilities_addressed': len(patched_versions),
            'upgrade_priority': calculate_upgrade_priority(vulnerabilities),
            'upgrade_steps': generate_upgrade_guide(current_version, recommended_version),
            'testing_recommendations': [
                'Backup production database before upgrade',
                'Test upgrade on staging environment',
                'Verify plugin compatibility with new version',
                'Plan maintenance window during low-traffic period'
            ],
            'estimated_downtime': estimate_upgrade_downtime(current_version, recommended_version)
        }
    else:
        return {
            'current_version': current_version,
            'recommendation': 'Current version adequate for detected issues',
            'alternative_mitigations': generate_config_recommendations(vulnerabilities)
        }
Configuration Hardening Recommendations:
def generate_hardening_recommendations(scan_results):
    """Generate configuration hardening recommendations"""
    
    recommendations = []
    
    # Analyze security headers
    missing_headers = analyze_security_headers(scan_results)
    if missing_headers:
        recommendations.append({
            'category': 'Security Headers',
            'priority': 'HIGH',
            'recommendations': [
                {
                    'item': 'Enable Content-Security-Policy',
                    'config_location': 'config.php',
                    'config_snippet': "$CFG->additionalhtmlhead = \"<meta http-equiv='Content-Security-Policy' content='...'>\";",
                    'impact': 'Mitigates XSS attacks'
                },
                {
                    'item': 'Enable X-Frame-Options',
                    'config_location': '.htaccess or nginx.conf',
                    'config_snippet': "Header always append X-Frame-Options SAMEORIGIN",
                    'impact': 'Prevents clickjacking attacks'
                }
            ]
        })
    
    # Analyze authentication configuration
    weak_auth = analyze_authentication_config(scan_results)
    if weak_auth:
        recommendations.append({
            'category': 'Authentication',
            'priority': 'CRITICAL',
            'recommendations': [
                {
                    'item': 'Enable password complexity requirements',
                    'config_location': 'Site administration → Security → Site policies',
                    'steps': [
                        'Set minimum password length to 12 characters',
                        'Require lowercase, uppercase, digits, and special characters',
                        'Enable password expiration (90 days recommended)'
                    ],
                    'impact': 'Reduces brute force attack success rate'
                },
                {
                    'item': 'Implement account lockout policy',
                    'config_location': 'Site administration → Security → Site policies',
                    'config_snippet': "$CFG->lockoutthreshold = 5;\n$CFG->lockoutwindow = 1800;",
                    'impact': 'Prevents credential stuffing attacks'
                }
            ]
        })
    
    # Analyze plugin security
    vulnerable_plugins = identify_vulnerable_plugins(scan_results)
    if vulnerable_plugins:
        recommendations.append({
            'category': 'Plugin Management',
            'priority': 'HIGH',
            'recommendations': [
                {
                    'item': f'Update or disable vulnerable plugins',
                    'affected_plugins': [p['name'] for p in vulnerable_plugins],
                    'actions': [
                        {
                            'plugin': p['name'],
                            'current_version': p['version'],
                            'safe_version': p['safe_version'],
                            'action': 'UPDATE' if p['update_available'] else 'DISABLE'
                        }
                        for p in vulnerable_plugins
                    ]
                }
            ]
        })
    
    return {
        'total_recommendations': len(recommendations),
        'critical_count': sum(1 for r in recommendations if r['priority'] == 'CRITICAL'),
        'high_count': sum(1 for r in recommendations if r['priority'] == 'HIGH'),
        'recommendations': recommendations,
        'implementation_priority': prioritize_recommendations(recommendations)
    }

CREATE TABLE alerts (
    id VARCHAR(36) PRIMARY KEY,
    session_id VARCHAR(36) NOT NULL,
    timestamp TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    vulnerability_type VARCHAR(50) NOT NULL,
    url TEXT NOT NULL,
    parameter VARCHAR(255),
    http_method VARCHAR(10),
    
    -- CVSS Scoring
    cvss_base DECIMAL(3,1),
    cvss_adaptive DECIMAL(3,1),
    severity ENUM('INFORMATIONAL', 'LOW', 'MEDIUM', 'HIGH', 'CRITICAL'),
    
    -- ML Classification
    ml_classification ENUM('TRUE_POSITIVE', 'FALSE_POSITIVE', 'UNCERTAIN'),
    ml_probability DECIMAL(4,3),
    ml_confidence DECIMAL(4,3),
    
    -- Risk Assessment
    risk_score DECIMAL(5,2),
    risk_priority ENUM('P1_CRITICAL', 'P2_HIGH', 'P3_MEDIUM', 'P4_LOW'),
    
    -- Evidence and Context (JSON columns)
    evidence_json JSON NOT NULL,
    context_json JSON NOT NULL,
    adjustment_factors_json JSON,
    
    -- References
    cwe_ids TEXT,
    references TEXT,
    
    -- Status tracking
    status ENUM('NEW', 'REVIEWED', 'MITIGATED', 'FALSE_POSITIVE', 'ACCEPTED_RISK') DEFAULT 'NEW',
    reviewed_by VARCHAR(255),
    reviewed_at TIMESTAMP,
    
    FOREIGN KEY (session_id) REFERENCES scan_sessions(id) ON DELETE CASCADE,
    INDEX idx_session (session_id),
    INDEX idx_severity (severity),
    INDEX idx_priority (risk_priority),
    INDEX idx_status (status),
    INDEX idx_timestamp (timestamp)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

Parallel Scanning Strategy:
def optimize_scan_performance(endpoints, available_resources):
    """
    Distribute scanning workload across multiple processes
    """
    
    # Calculate optimal parallelism
    cpu_cores = available_resources['cpu_cores']
    memory_gb = available_resources['memory_gb']
    
    # Conservative: 1 scanner per 2 cores, min 2GB per scanner
    max_parallel_scanners = min(
        cpu_cores // 2,
        int(memory_gb // 2),
        10  # Hard limit to prevent resource exhaustion
    )
    
    # Partition endpoints by complexity
    endpoint_groups = partition_by_complexity(endpoints)
    
    # Priority queue: scan high-value targets first
    priority_queue = []
    for endpoint in endpoints:
        priority = calculate_scan_priority(endpoint)
        priority_queue.append((priority, endpoint))
    
    priority_queue.sort(reverse=True)  # Highest priority first
    
    # Distribute work
    scanner_queues = [[] for _ in range(max_parallel_scanners)]
    for i, (priority, endpoint) in enumerate(priority_queue):
        queue_index = i % max_parallel_scanners
        scanner_queues[queue_index].append(endpoint)
    
    return {
        'parallel_scanners': max_parallel_scanners,
        'scanner_queues': scanner_queues,
        'estimated_duration': estimate_duration(scanner_queues)
    }

def incremental_scan_strategy(last_scan_timestamp):
    """
    Focus on changed/new endpoints since last scan
    """
    
    # Identify changes since last scan
    changes = detect_changes_since(last_scan_timestamp)
    
    scan_scope = {
        'new_endpoints': changes['new_endpoints'],
        'modified_endpoints': changes['modified_endpoints'],
        'always_scan': [
            '/admin/*',  # Admin panel always scanned
            '/login/*',  # Authentication always scanned
            '/webservice/*'  # API always scanned
        ]
    }
    
    # For unchanged endpoints: quick validation scan only
    scan_scope['validation_only'] = [
        ep for ep in changes['unchanged_endpoints']
        if not matches_pattern(ep, scan_scope['always_scan'])
    ]
    
    return scan_scope

function cleanup_old_scan_data() {

    $retention_policies = [

            'risk_priority = ? AND timestamp < ?',

        );
    }
}

function log_security_event($event_type, $details) {
    global $DB, $USER;
    
    $log_entry = new stdClass();
    $log_entry->timestamp = time();
    $log_entry->event_type = $event_type;
    $log_entry->user_id = $USER->id;
    $log_entry->ip_address = getremoteaddr();
    $log_entry->details = json_encode($details);
    $log_entry->user_agent = $_SERVER['HTTP_USER_AGENT'] ?? '';
    
    $DB->insert_record('tool_adaptivesecurity_audit', $log_entry);
    
    // For critical events, also log to syslog
    if (in_array($event_type, ['MITIGATION_APPLIED', 'SCAN_FAILED', 'UNAUTHORIZED_ACCESS'])) {
        syslog(LOG_WARNING, "AdaptiveSecurity: $event_type - " . json_encode($details));
    }
}

BAB III - PENUTUP
Perancangan sistem Adaptive Security Proxy untuk Moodle telah disusun dengan arsitektur berlapis yang komprehensif, mengintegrasikan Dynamic Application Security Testing, machine learning optimization, adaptive CVSS risk scoring, dan mekanisme semi self-healing. Desain four-layer architecture memberikan balance optimal antara akurasi deteksi, efisiensi operasional, dan kontrol manusia dalam pengambilan keputusan kritis.
Penggunaan Docker containerization untuk isolasi lingkungan pengujian memastikan bahwa aktivitas scanning tidak mengganggu operasional sistem produksi Moodle. Integrasi machine learning pada Layer 2 secara signifikan mengurangi false positive rate, sementara adaptive CVSS scoring pada Layer 3 memberikan penilaian risiko yang kontekstual dan akurat. Mekanisme semi self-healing pada Layer 4 memberikan kemampuan respons otomatis untuk threat dengan confidence tinggi, namun tetap mempertahankan human oversight untuk keputusan dengan impact signifikan.
Implementasi sistem yang akan dilakukan pada BAB IV akan mengikuti desain arsitektur dan spesifikasi teknis yang telah diuraikan dalam bab ini. Pengujian dan evaluasi pada BAB V akan memvalidasi efektivitas setiap layer dalam mencapai tujuan penelitian yang telah ditetapkan.
